= ADR 015: Credential Storage in a dedicated `account` table

== Context

Authenticating members (xref:adr-013.adoc[ADR 013]) requires storing credential data, in addition to the existing `member` table that models household membership itself. Not every `member` necessarily has a login identity of its own: once social login is added, some accounts may authenticate purely via a federated provider without ever setting a local password, and a member does not automatically need an account at all.

== Considered Options

Credential fields as additional columns directly on `member`; a dedicated `account` table with a 1:1 relation to `member` (consistent with the 1:1 account-household cardinality decided in xref:adr-012.adoc[ADR 012]).

== Decision Outcome

Credentials are stored in a dedicated `account` table, related 1:1 to `member`.

`member` models the household-membership domain; `account` models the login identity, a security concern rather than household business. Adding password/verification columns directly to `member` would mix these two concerns and bloat the household-membership aggregate with fields that have nothing to do with household business. A separate `account` table keeps that separation without introducing a new module - it stays inside the `household` schema, alongside `member`, since xref:../chapters/08_concepts.adoc[Chapter 8] already establishes that authentication is a cross-cutting concern handled within `household`, not a bounded context of its own.

The 1:1 relation is also optional by nature: since not every `member` has - or ever will have - a login identity, and since a future account may be entirely federated (no password hash at all), a nullable set of authentication columns directly on `member` would be a worse fit than a separate row that simply does not exist for members without an account.
