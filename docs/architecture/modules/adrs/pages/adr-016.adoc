[[adr-016]]
= ADR 016: Backend-Side (BFF) Social Login Federation

IMPORTANT: This decision was revised on 2026-11-03. The original decision (2026-10-07) let the embedded Authorization Server federate to external providers on its own login page; see <<decision-history>> for what changed and why.

== Context

Adding social login (Google, GitHub, Microsoft, self-hosted generic OIDC) requires deciding how the SPA, the backend, and the external providers fit together.
The backend authenticates with a session only (xref:adr-013.adoc[ADR 013]), and xref:adr-014.adoc[ADR 014] keeps all tokens out of the browser.
A successful external login has to end in the same kind of session as a local password login, so that account-status enforcement and session handling are the same for every login path.

== Considered Options

. The backend is the only, confidential OAuth2/OIDC client of each external provider, using Spring Security's `oauth2Login()` in its single filter chain (backend-side federation, BFF).
. Multi-client registration: the SPA authenticates directly against external providers and the backend only validates externally issued tokens as a resource server.

== Decision Outcome

Option 1. The SPA starts a social login with a top-level navigation to `/oauth2/authorization/{registrationId}`; the provider redirects back to the backend's callback `/login/oauth2/code/{registrationId}`.
Spring Security handles the Authorization Code flow with PKCE, `state` and, for OIDC registrations, `nonce` and ID-token validation.
The callback resolves the external identity to the local account (xref:adr-018.adoc[ADR 018]) and replaces the external authentication with the same session principal a local login yields; the provider tokens are discarded in the callback.
Providers are configured with Spring Boot's standard `spring.security.oauth2.client.*` properties; a startup check rejects registrations that would not deliver a usable identity (see xref:../chapters/07_deployment_view.adoc#section-social-login-provider-requirements[Chapter 7]).

Option 2 was rejected because it would let external provider tokens reach the browser - exactly the exposure xref:adr-014.adoc[ADR 014]'s BFF/cookie model was adopted to avoid - and would scatter trust across multiple issuers and sessions instead of the one session the BFF model relies on.

== Pros and Cons of the Options

.Overview of the pros and cons of the considered options
[cols="2a,2a"]
|===
|Pros |Cons

2+^s|Backend-side federation via `oauth2Login()` (chosen)
|
- Tokens never reach the browser, consistent with ADR 014; provider tokens do not outlive the callback
- One session and one principal for every login path; lockout and verification enforcement apply uniformly
- Standard Spring Boot provider configuration, no custom client registration code
|
- The backend is a confidential client of each provider; self-hosters must register it there and configure scopes explicitly

2+^s|Multi-client registration
|
- No federation logic needed in the backend
|
- External provider tokens would reach the browser, breaking ADR 014
- Multiple issuers/JWKS to trust, multiple parallel sessions, no single logout

|===

== Decision History

[cols="1,2a,3a"]
|===
|Date |Decision |Reason for the change

|2026-10-07
|Authorization-Server-side federation: the embedded Spring Authorization Server (then ADR 013) becomes an OAuth2/OIDC client of the external providers on its own login page, following Spring Authorization Server's "How-to: Authenticate using Social Login" guide. The SPA keeps talking to exactly one issuer for local and federated logins.
|Initial decision.

|2026-11-03
|Backend-side federation via `oauth2Login()` in the single session-based filter chain.
|
- The embedded Authorization Server was removed (xref:adr-013.adoc[ADR 013]); there is no own issuer to federate through anymore.
- The original goal - provider tokens never reach the browser, one session for all login paths - is kept and reached with less machinery: no second login step through the loop-back client, no custom client registration repository, no separate principal type for federated logins.
- The change happened before the first release; no data or clients had to be migrated.
|===
