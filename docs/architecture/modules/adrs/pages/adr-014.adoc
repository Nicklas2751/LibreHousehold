= ADR 014: Session Strategy - Backend for Frontend (BFF) with httpOnly Cookies

== Context

After logging in (xref:adr-013.adoc[ADR 013]), the SPA needs a way to stay authenticated against the backend for subsequent requests. The logged-in state could either be represented by tokens handed to the frontend to hold and send itself (the classic SPA bearer-token pattern), or kept entirely on the backend, exposing only an opaque session identifier to the browser. The backend issues no tokens of its own; the only tokens involved are those of external social-login providers (xref:adr-016.adoc[ADR 016]). This also has to fit the project's existing rule that no state is persisted in `localStorage`/`sessionStorage` in the frontend.

== Considered Options

Backend for Frontend (BFF) pattern with an httpOnly, SameSite session cookie (no token ever reaches the browser); tokens held directly in the frontend (`localStorage`, `sessionStorage`, or an in-memory JS variable, the classic SPA bearer-token pattern).

== Decision Outcome

The BFF pattern is used: the HTTP session is the only credential, and the browser only ever receives an opaque, httpOnly, SameSite session cookie. Tokens of external providers never leave the backend and do not even outlive the login callback: the backend uses them once to identify the external account and then discards them. This is consistent with the project's already-established rule that no state is persisted in `localStorage`/`sessionStorage` on the frontend - a token-in-frontend model would need exactly that, or an equally exposed in-memory JS variable, either of which is reachable by an XSS payload. Keeping tokens out of the JavaScript context entirely removes that attack surface and matches the pattern recommended by IETF's "OAuth 2.0 for Browser-Based Apps" BCP for browser-based OAuth2 clients.

Because cookies are sent automatically by the browser, the BFF must guard explicitly against CSRF: Spring Security's cookie-based CSRF protection is used, i.e. a readable `XSRF-TOKEN` cookie plus a matching `X-XSRF-TOKEN` request header that the SPA echoes back on state-changing requests; the server rejects requests where the header is missing or does not match.

Logout (`POST /v1/logout`) does not just delete the session cookie client-side. It invalidates the session on the server and deletes the session cookie, so a copied or previously leaked session ID cannot be replayed after logout. The response carries a fresh `XSRF-TOKEN` for the now anonymous client. There is nothing to revoke beyond that: the backend holds no tokens of its own, and provider tokens are already gone after the login callback.

NOTE: Revised on 2026-11-03 together with xref:adr-013.adoc[ADR 013]. The decision for the BFF pattern is unchanged; the previous wording assumed tokens issued by an embedded Authorization Server and a logout that revokes them. That revocation was never implemented, and with the Authorization Server removed there are no such tokens.
