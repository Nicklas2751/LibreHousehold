== Risks and Technical Debts

This chapter collects the technical risks and technical debts that have already surfaced elsewhere in this documentation (ADRs, Chapter 5) and in the project's implementation notes, so they are visible in one place instead of scattered across individual decision records. Each entry is ordered by priority within its table and links back to where it was originally identified.

* A **Technical Debt** is a known, already-accepted shortcut or gap in the current implementation.
* A **Risk** is something that has not happened yet but could, if the architecture is not watched.

=== Technical Debt

[cols="1,4,2,1,3", options="header"]
|===
|ID |Description |Affects |Priority |Mitigation / Next Step

|TD1
|Module boundaries are only partially technically enforced: `ApplicationTests.writeDocumentationSnippets` already calls `ApplicationModules.verify()` on every build, which catches structural cycles between modules (it has already caught a real cycle during the P2.2 implementation). However, no `package-info.java` with `@ApplicationModule(allowedDependencies = ...)` exists in the backend yet, even though xref:../adrs/adr-011.adoc[ADR 011] mandates explicit, declared dependencies between modules. Without that declaration, `verify()` has no explicit allow-list to check a module's dependencies against beyond cycle detection, so nothing but code review discipline stops a module from importing another module's internals as long as no cycle results. Authentication adds cross-module wiring of this kind: `config` signs federated accounts in through `household`'s `AccountSignIn` Named Interface, and `session` depends on `config` only through the `config`-owned `SocialLoginContextStore`.
|xref:01_introduction_and_goals.adoc#QG4[QG4 - Maintainable]
|High
|Add `package-info.java` per module declaring `allowedDependencies`, as already specified in ADR 011 — the existing `ApplicationModules.verify()` test will then also enforce it.

|TD2
|No server-side limit on uploaded image size: `server.tomcat.max-http-post-size` is set to unbounded (`-1`) and the OpenAPI `image`/`avatar` fields have no `maxLength` constraint, so a client can currently upload an arbitrarily large base64-encoded image.
|xref:01_introduction_and_goals.adoc#QG2[QG2 - Secure]
|High
|Enforce a maximum image size (recommended: 5 MB) via Bean Validation or a servlet filter.

|TD3
|No image content validation: uploaded `image`/`avatar` base64 payloads are not checked to actually be a valid JPEG/PNG/WebP file (no magic-byte or MIME-type detection).
|xref:01_introduction_and_goals.adoc#QG2[QG2 - Secure]
|Medium
|Add magic-byte or MIME-type detection before persisting an uploaded image.

|TD4
|`tasks` and `expenses` have a compile-time dependency on `household`'s public interfaces (Named Interfaces). This is an intentional, accepted trade-off (see xref:../adrs/adr-011.adoc[ADR 011]), not an oversight.
|xref:01_introduction_and_goals.adoc#QG4[QG4 - Maintainable]
|Low _(accepted)_
|No action needed now. Keep the interfaces narrow (see xref:05_building_block_view.adoc#section-subdomain-classification[Chapter 5, Bounded Context Map]) so extraction to microservices stays cheap if that is ever needed.
|===

=== Risks

[cols="1,4,2,1,3", options="header"]
|===
|ID |Description |Affects |Priority |Mitigation / Next Step

|R1
|`Household`'s Named Interfaces could grow into a coupling bottleneck if future consumers are given bespoke, per-consumer query methods instead of narrow, generic ones (see xref:05_building_block_view.adoc[Chapter 5, Bounded Context Map]).
|xref:01_introduction_and_goals.adoc#QG4[QG4 - Maintainable]
|Medium
|Review new Named Interface methods for genuine reuse before adding them; if the interface grows wide, redesign it rather than splitting `Household`.

|R2
|The eventual-consistency window between a producing transaction's commit and the asynchronous `@ApplicationModuleListener` execution (xref:../adrs/adr-011.adoc[ADR 011]) could silently be relied upon somewhere that actually needs immediate consistency.
|xref:01_introduction_and_goals.adoc#QG2[QG2 - Secure], xref:01_introduction_and_goals.adoc#QG4[QG4 - Maintainable]
|Medium
|Enforce in code review: Domain Events are for reactive cleanup/notifications only, never for logic that needs read-your-write consistency within the same request.

|R3
|The 1 Account : 1 Household model (xref:../adrs/adr-012.adoc[ADR 012]) is a deliberate scope decision. If multi-household usage under a single login is ever required, this becomes a breaking model change (extracting `Account` out of `household`).
|xref:01_introduction_and_goals.adoc#QG4[QG4 - Maintainable]
|Low
|No action needed now; revisit only if this product requirement actually materializes.

|R4
|Java is more verbose than modern alternatives such as Kotlin (accepted trade-off in xref:../adrs/adr-002.adoc[ADR 002]), which can increase boilerplate and slow down new contributors.
|xref:01_introduction_and_goals.adoc#QG4[QG4 - Maintainable]
|Low
|Favor idiomatic modern Java (records, `var`, pattern matching) to keep boilerplate low; no framework change planned.

|R5
|No check against known/breached passwords is performed at registration or password change (ASVS 5.0 V6.2.4/V6.2.12), a deliberate choice to avoid an external dependency (e.g. an online breach-check API) or a wordlist to maintain (see xref:08_concepts.adoc#section-security-controls-authentication[Chapter 8, Security Controls (Authentication), PW3]). Users can therefore still choose a password that is already known to be compromised.
|xref:01_introduction_and_goals.adoc#QG2[QG2 - Secure]
|Medium _(accepted)_
|No action planned. If weak/breached passwords become an actual problem, consider a static top-N common-password blocklist bundled at build time (no runtime external dependency) before reaching for an online breach-check API.

|R6
|Lockout denial of service: an attacker who knows a member's e-mail address can keep that account locked by repeating failed logins, because every failed attempt after an expired lock locks the account again (intended lockout policy, see xref:08_concepts.adoc#section-security-controls-authentication[Chapter 8, RATE1]). The per-IP login limit slows this down but does not prevent it from several IPs.
|xref:01_introduction_and_goals.adoc#QG2[QG2 - Secure]
|Medium _(accepted)_
|A password reset lifts the lockout immediately, so the owner of the mailbox can always get back in. No change to the lockout policy planned.

|R7
|No token-based API: the HTTP session is the only credential (xref:../adrs/adr-013.adoc[ADR 013]). Native apps, other non-browser clients or third-party integrations cannot access the API with tokens.
|xref:01_introduction_and_goals.adoc#QG4[QG4 - Maintainable]
|Low _(accepted)_
|No action needed now. ADR 013 names the conditions under which an Authorization Server returns and how (`oauth2ResourceServer()` for the affected APIs, the SPA stays on the session).

|R8
|No multi-factor authentication (ASVS 5.0 V6.3.3, L2): a local account is protected by its password only, so the L2 baseline of xref:08_concepts.adoc#section-security-controls-authentication[Chapter 8] is not fully met. Social login inherits whatever the provider enforces.
|xref:01_introduction_and_goals.adoc#QG2[QG2 - Secure]
|Medium
|Not planned yet. The single sign-in pipeline per path (AUTH1 in Chapter 8) is the place where a second factor would be added.

|R9
|Session lifetime and persistence: sessions use the servlet container's default idle timeout (30 minutes) without an absolute lifetime, and they are held in memory, so every backend restart or redeployment logs all users out, and the backend cannot be replicated without sticky sessions.
|xref:01_introduction_and_goals.adoc#QG1[QG1 - Easy to learn], xref:01_introduction_and_goals.adoc#QG3[QG3 - Easy to host]
|Medium
|Decide on an explicit idle and absolute session lifetime; persist sessions (e.g. Spring Session JDBC) once restarts or replication make the logouts noticeable.

|R10
|Member and household IDs are generated by the client (offline-first), so an ID can be reused after its owner was deleted: (a) a new registration with the ID of a deleted member takes over that member's still-open sessions, because sessions are identified by the member ID; (b) tasks and expenses reference the member ID without a foreign key and are inherited by the new member; (c) a new household with the ID of a deleted one inherits data of other modules whose cleanup after the deletion event has failed.
|xref:01_introduction_and_goals.adoc#QG2[QG2 - Secure]
|Medium
|(a) Mitigated: removing a member or deleting a household ends the members' sessions (SES7 in xref:08_concepts.adoc[Chapter 8]), so no open session is left to take over. (b) and (c) are accepted; server-generated IDs are not planned, because they would break creating data offline.
|===
